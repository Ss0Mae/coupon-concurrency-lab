# EXP-05 — 발급 가능 상태 지속 부하: 어느 동시 사용자 수부터 무엇이 병목인가

```text
실험 이름: sustained — 쿠폰 10,000,000개(품절 없음), 10초 지속 부하, 매 요청 새 사용자
검증하려는 가설:
  (1) 성공 경로만 있는 부하에서 정합 전략 3종의 처리량 상한은 커넥션 수가 아니라 coupon 1행(핫로우)의 갱신 직렬화다.
  (2) 동시 사용자 증가에 따라 HikariCP 커넥션 대기 → Tomcat 스레드 대기 순으로 병목이 옮겨 가고, p95 는 그 지점에서 꺾인다.
  (3) 락 없음은 초과 발급이 불가능한 조건(재고 무제한)에서도 lost update 로 재고 불일치를 남긴다.
변경한 항목: 전략만 변경. k6 MODE=duration(constant-vus 10초).
통제한 조건: EXP-01 과 동일한 앱/DB/풀(20)/JVM 옵션. 실행 전 초기화. 5회 반복, 순서 회전 (워밍업은 같은 JVM 에서 EXP-01·02 직후라 생략).
서버 및 DB 사양: EXP-01 과 동일
테스트 데이터: coupon 1행(total_quantity=10,000,000), coupon_issue 0행, userId 는 실행 내 유일
동시 사용자: 10 → 50 → 100 → 200 → 500 → 1,000
전체 요청 수: 10초 동안 도달한 요청 수 — 전략·VU 에 따라 2,500~11,300건 (표의 TPS × 10)
테스트 지속시간: 실행당 10초 (k6 gracefulStop 포함 최대 약 12초)
```

```text
병목 원인 (조건부 UPDATE 기준, 비관적 락도 같은 형태):
  10 VU  — 커넥션 대기 0, 그러나 행 잠금 대기가 요청마다 1회(6,324회, 평균 13.6 ms). 이미 핫로우 직렬화가 응답시간의 대부분이다.
           TPS 623 ≈ 1 / 1.6 ms: 성공 1건당 핫로우 독점 구간(UPDATE~COMMIT, fsync 포함)이 약 1.6 ms 라는 뜻.
  50 VU  — 풀(20)을 넘겨 대기 커넥션 max 30, 획득 평균 64.5 ms, 행 잠금 대기 평균 40.4 ms → p95 24 → 222 ms(9배). TPS 는 462 로 오히려 하락.
  100~200 VU — 획득 대기 118 → 205 ms, 대기 커넥션 80 → 179. p95 303 → 621 ms. TPS 는 666 → 855 로 증가:
           잠금 대기자가 많을수록 InnoDB 그룹 커밋이 fsync 를 묶어 주는 효과로 해석하지만 이 실험에서 직접 검증하지는 않았다(가설).
  500 VU — 대기 커넥션 max 가 179 에서 더 늘지 않는다 = Tomcat 스레드 200 이 상한. 나머지 300 요청은 Tomcat 큐에서 대기.
           획득 대기는 204 ms 로 그대로인데 p95 가 621 → 2,051 ms(3.3배)로 꺾인다. 응답시간 증가분은 DB 가 아니라 Tomcat 큐 대기.
  1,000 VU — 같은 이유로 p95 1.8초(조건부) / 3.3초(비관적). TPS 조건부 1,132 vs 비관적 623 — 잠금 보유 구간이 짧은 쪽이
           높은 경합에서 유리(비관적 락은 SELECT FOR UPDATE ~ INSERT ~ UPDATE ~ COMMIT 전체를 잠근다).
  낙관적 락 — 모든 VU 에서 충돌이 요청의 수십 배(10초에 2~4만 회), MySQL CPU 65~107% 로 유일하게 CPU 병목. 5xx 30~66%.
해석:
  가설 (1) 확인: 커넥션 풀·CPU 어느 것도 포화되지 않았는데 TPS 는 460~1,130 에 머문다(EXP-03 풀 크기 실험과 일치).
  가설 (2) 확인: 병목 이동 순서는 핫로우 잠금(10 VU) → 커넥션 풀 대기(50 VU) → Tomcat 스레드 큐(500 VU). p95 는 50 VU 에서 9배, 500 VU 에서 3.3배 꺾인다.
  가설 (3) 확인: 락 없음은 초과 발급이 없어도 재고-발급 불일치 수천 건.
  비관적 락 → 조건부 UPDATE 개선율: 200 VU TPS +24.4%, p95 −7.7%, p99 +15.1%(악화), 잠금 대기 평균 −20.7%, 커넥션 획득 −19.7%;
  1,000 VU TPS +81.8%, p95 −45.2%, p99 −45.8%, 잠금 대기 평균 −46.7%, 커넥션 획득 −45.0%.
  낙관적 락 → 조건부 UPDATE: 200 VU TPS +206%, p95 −77.5%, 오류율 46.55%p → 0. 단 잠금 대기 평균은 +424% — 낙관적 락은 잠금을 거의 안 잡는 대신 CPU 로 스핀한다.
부작용:
  성공 경로만 있는 부하에서 비관적 락과 조건부 UPDATE 의 차이는 200 VU 이하에서 작고 5회 편차(TPS CV 10~25%)에 묻힐 수 있다.
  p99 는 200 VU 에서 조건부가 더 나쁘게 측정됐다(2,048 vs 1,779 ms). 같은 장비의 k6·Docker VM 잡음이 p99 에 크게 반영된다.
  10초 실행 5회의 편차가 크다. 순서 효과를 회전으로 상쇄했지만 장비 공유 잡음은 제거하지 못했다.
결론:
  선착순 쿠폰의 성공 경로 상한은 "핫로우 1행의 커밋 직렬화(≈1.6 ms/건)"이며, 전략 선택은 그 상한 아래에서 잠금 보유 시간과 실패 비용을 줄이는 문제다.
  조건부 UPDATE 는 잠금 보유가 가장 짧고 재시도·CPU 비용이 없어 모든 VU 에서 정합 전략 중 최고 또는 동급. 낙관적 락은 핫로우에 부적합.
```
