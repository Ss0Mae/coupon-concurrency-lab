# EXP-01 — 정합성·선착순 시나리오: 쿠폰 100개, 서로 다른 사용자 1,000명

```text
실험 이름: coherence — 쿠폰 100개에 서로 다른 사용자 1,000명이 동시 요청 (요청 1,000건 고정)
검증하려는 가설:
  (1) 읽고-검사하고-쓰는 락 없는 구현은 초과 발급이 발생한다.
  (2) 비관적 락·낙관적 락·조건부 UPDATE 는 초과 발급·중복 발급·재고 불일치가 0건이다.
  (3) 조건부 UPDATE 는 핫로우 락 보유 구간이 짧고 품절 경로에 락이 없어 비관적 락보다 TPS 가 높고 p95 가 낮다.
변경한 항목: 발급 전략(URL 경로 no-lock / pessimistic / optimistic / conditional)만 변경. 코드·설정·데이터는 동일.
통제한 조건: 같은 장비, JVM 옵션(-Xms1g -Xmx1g G1), Tomcat 200 스레드, HikariCP 20 고정, MySQL 설정, 쿠폰 수량 100,
  요청 1,000건(shared-iterations), 같은 k6 스크립트, 실행 전 TRUNCATE coupon_issue + issued_quantity=0 + version=0,
  전략별 워밍업 1회(200 VU) 후 5회 반복, 반복마다 전략 순서 회전.
서버 및 DB 사양: Apple M5 10코어 32 GB (앱·k6·Docker VM 공유), Spring Boot 4.1 / Java 21,
  MySQL 8.0.46 Docker(cpus=4, 1.5 GiB, buffer pool 512 MB, REPEATABLE READ, innodb_flush_log_at_trx_commit=1)
테스트 데이터: coupon 1행(total_quantity=100), coupon_issue 0행, userId 1..1000 각 1회
동시 사용자: 10 → 50 → 100 → 200 → 500 → 1,000 (VU)
전체 요청 수: 단계당 1,000건 × 4전략 × 5회 = 120,000건 (+ 워밍업)
테스트 지속시간: 요청 1,000건을 소진할 때까지 (0.2~1.6초, 전략·VU 에 따라 다름)
```

```text
병목 원인:
  락 없음 — 재고 검사가 트랜잭션 스냅샷의 issued_quantity 를 기준으로 하므로 1,000명 모두 "재고 있음"을 보고 INSERT.
    UPDATE 는 절대값(읽은 값+1)이라 동시 갱신이 서로 덮어써 issued_quantity 가 52 에서 멈춤(lost update). 10 VU 에서도 1,000건 발급.
    행 잠금 대기 합계 20,265 ms — 1,000건 전부 핫로우 UPDATE 를 실행하므로 잠금 대기가 가장 많다.
  비관적 락 — 품절 판정(900건)까지 SELECT ... FOR UPDATE 로 핫로우를 잡는다 → 요청 1,000건마다 잠금 대기 1회(999회).
    잠금 보유 구간이 SELECT~COMMIT 이라 INSERT 까지 직렬화된다. 커넥션 획득 평균 52.9 ms.
  낙관적 락 — 성공 100건을 위해 version 충돌 1,895회, 재시도 1,856회 → SELECT 가 1,994회로 2배, 재시도 20회 소진 503 이 38건(3.8%).
    핫로우 하나를 두고 낙관적 재시도는 스핀에 가깝다.
  조건부 UPDATE — 무잠금 선조회가 품절 900건을 걸러 UPDATE 는 119회만 실행, 잠금 대기 118회.
    잠금 1회당 대기 25.6 ms 는 UPDATE~COMMIT(fsync 포함) 직렬화 구간이며, 합계는 비관적 락의 절반(3,016 ms).
해석:
  정합성은 비관적·낙관적·조건부 모두 5회 × 6단계 전부 초과 0 / 중복 0 / 불일치 0. 락 없음은 매번 900건 초과.
  성능은 조건부 UPDATE > 비관적 락 > 낙관적 락 > 락 없음. 1,000 VU 에서 비관적 락 대비 TPS +32.9%, p95 −25.4%, p99 −22.2%,
  행 잠금 대기 합계 −50.1%, 커넥션 획득 대기 −33.2%. 50 VU 부터 조건부 UPDATE 가 비관적 락보다 p95 가 낮고, 격차는 200 VU 에서 가장 크다(125.7 vs 187.2 ms).
  낙관적 락은 50 VU 부터 p95 가 300 ms 를 넘고 모든 단계에서 3~7% 의 503 이 발생해 선착순 핫로우에는 부적합하다.
  이상치: 비관적 락 1,000 VU 1·2회차(1,725 / 1,843 TPS, 커넥션 대기 최대 179)가 3~5회차(2,590~3,137)보다 느렸다. 원인은 특정하지 못했고
  같은 장비에서 k6(1,000 VU)·JVM·Docker VM 이 CPU 를 나눠 쓰는 환경 잡음으로 본다. 중앙값을 대표값으로 쓴 이유다.
부작용:
  조건부 UPDATE 의 선조회는 무잠금이라 품절 경계에서 INSERT 후 UPDATE 0행 → 롤백이 발생한다(UPDATE 119회 중 19회, ROLLBACK 19회). 결과는 옳지만 헛일이다.
  잠금 1회당 평균 대기(25.6 ms)는 비관적 락(6.05 ms)보다 길다. 대기 횟수가 1/8 이라 합계는 절반이지만 "평균 락 대기시간" 하나만 보면 나빠진 것처럼 보인다.
  1초 안에 끝나는 실행이라 Prometheus 1초 표본 기반 지표(활성/대기 커넥션, CPU)는 이 실험에서 신뢰하지 않는다.
결론:
  가설 (1)(2)(3) 모두 실측으로 확인. 최종 후보는 조건부 UPDATE. 낙관적 락은 정합성은 맞지만 오류율·p95 때문에 탈락.
```
