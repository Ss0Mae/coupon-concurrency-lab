# EXP-07 — 재고가 남아 있는 상태의 중복 요청: 2번째 요청은 반드시 409 인가

```text
실험 이름: dupopen — 쿠폰 10,000,000개(품절 없음), 사용자 1,000명 × 2회 = 2,000건, 동시 사용자 1,000명
검증하려는 가설: 품절 빠른 경로가 개입하지 않으면 모든 전략에서 2번째 요청은 UNIQUE 제약에 걸려 409 가 되고, DB 발급은 정확히 1,000건이다.
변경한 항목: EXP-02 에서 쿠폰 수량만 100 → 10,000,000. 나머지 동일.
통제한 조건: EXP-01 과 동일 (풀 20, Tomcat 200, 5회 반복, 순서 회전, 실행 전 초기화)
서버 및 DB 사양: EXP-01 과 동일
테스트 데이터: coupon 1행(total_quantity=10,000,000), coupon_issue 0행, userId = 1 + i % 1000
동시 사용자: 1,000
전체 요청 수: 2,000 × 4전략 × 5회 = 40,000건
테스트 지속시간: 요청 2,000건 소진까지 (1.0~6.5초)
```

## 측정 결과 (5회 중앙값, 정합성 값은 5회 중 최악)

| 구현 방식 | 성공 응답 | 중복 차단(409) | 품절(410) | 5xx | DB 발급 건수 | 고유 사용자 | 중복 발급 | 재고-발급 불일치 | TPS | p95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 락 없음 | 1,000 | 1,000 | 0 | 0 | 1,000 | 1,000 | 0 | 949 | 1,649.6 | 857.9 ms |
| 비관적 락 | 1,000 | 1,000 | 0 | 0 | 1,000 | 1,000 | 0 | 0 | 1,467.3 | 890.3 ms |
| 낙관적 락 | 833 | 557 | 0 | 618 | 839 | 822 | 0 | 0 | 376.7 | 3,665.2 ms |
| 조건부 UPDATE | 1,000 | 1,000 | 0 | 0 | 1,000 | 1,000 | 0 | 0 | 2,095.9 | 660.9 ms |

```text
병목 원인: 성공 1,000건이 전부 핫로우 UPDATE 를 거치므로 EXP-05 와 같은 핫로우 직렬화. 낙관적 락은 충돌 재시도 소진(503)이 618건(31%)이라
  1번째 요청이 실패한 사용자의 2번째 요청이 성공하는 식으로 성공 833·중복 557 로 갈라졌다. 응답과 DB 는 일치한다(성공 응답 = DB 행).
해석: 가설 확인. 락 없음·비관적·조건부 모두 성공 정확히 1,000 / 409 정확히 1,000 / DB 1,000행 / 고유 사용자 1,000 → 중복 발급 0.
  락 없음은 여기서도 재고-발급 불일치 949 건(lost update)을 남긴다. 낙관적 락은 중복은 없지만 5xx 31% 로 정상 종료율 69%.
부작용: 없음(검증 실험). 단 이 결과는 UNIQUE 제약이 있을 때의 이야기다 → EXP-04.
결론: 중복 차단은 UNIQUE(coupon_id, user_id) 제약 한 줄로 네 전략 모두에서 완전하다. 조건부 UPDATE 가 TPS 2,096 / p95 661 ms 로 가장 빠르다.
다음 실험: EXP-04 UNIQUE 제약 제거.
```
