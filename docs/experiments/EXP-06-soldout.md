# EXP-06 — 품절 상태 처리 성능: 잠금 없는 품절 경로의 가치

```text
실험 이름: soldout — 쿠폰 0개(처음부터 품절), 10초 지속 부하, 발급 가능 상태(EXP-05)와 비교
검증하려는 가설:
  (1) 선착순 이벤트 트래픽의 대부분은 품절 이후 도착하므로 품절 경로의 비용이 전체 처리량을 좌우한다.
  (2) 비관적 락은 품절 판정에도 SELECT ... FOR UPDATE 로 핫로우를 잠그므로, 무잠금 선조회를 쓰는 나머지 전략보다 품절 처리량이 낮다.
변경한 항목: 쿠폰 total_quantity=0. 전략만 변경. 나머지는 EXP-05 와 동일.
통제한 조건: EXP-05 와 동일 (풀 20, Tomcat 200, 10초, 5회 반복, 순서 회전)
서버 및 DB 사양: EXP-01 과 동일
테스트 데이터: coupon 1행(total_quantity=0, issued_quantity=0), coupon_issue 0행
동시 사용자: 100, 1,000
전체 요청 수: 10초 동안 도달한 요청 수 — 전략별 약 39,000~150,000건 (표의 TPS × 10)
테스트 지속시간: 실행당 10초
```

```text
병목 원인:
  품절 경로는 SELECT 1회로 끝난다. 무잠금 SELECT 는 평균 0.05 ms 라 병목이 DB 잠금에서 CPU 로 옮겨 간다:
  MySQL CPU 130~142%(4 vCPU 중 1.4코어), JVM 15~18%. 1,000 VU 에서 p95 117~147 ms 는 Tomcat 200 스레드 큐 대기다.
  비관적 락은 품절인데도 요청마다 행 X-락을 잡는다(잠금 대기 = 요청 수, 평균 3.3~3.6 ms). 그래서 SQL 평균이 70배 느리고(3.4~3.6 ms),
  TPS 는 다른 전략의 37~38% 에 그친다. CPU 는 남는데(53~56%) 잠금이 직렬화한다.
해석:
  가설 (1): 같은 전략에서 품절 상태는 발급 가능 상태보다 9~45배 빠르다. 선착순 요청 1,000건 중 900건이 품절 응답인 EXP-01 에서
  조건부 UPDATE 가 비관적 락보다 TPS 32.9% 높았던 이유의 대부분이 이 경로 차이다.
  가설 (2) 확인: 비관적 락 4,989 vs 조건부 13,025 TPS(100 VU, −61.7%), 5,373 vs 14,233 TPS(1,000 VU, −62.3%). p95 28.5 vs 15.9 ms, 216 vs 117 ms.
  락 없음·낙관적 락·조건부 UPDATE 의 품절 경로는 코드가 같아(무잠금 SELECT → 410) 성능도 같다. 편차(10,900~14,900)는 장비 잡음.
부작용:
  무잠금 선조회는 REPEATABLE READ 스냅샷을 읽으므로 "방금 품절됐는데 재고 있음"으로 판정할 수 있다. 그 경우 INSERT 후 UPDATE 0행으로 롤백해
  정합성은 지키지만(EXP-01 의 UPDATE 119회 중 19회) 품절 직전 순간의 요청은 헛일을 한다. 반대로 비관적 락은 품절 판정이 항상 최신값이다.
  품절 경로가 CPU 병목이 되면 애플리케이션 캐시(품절 플래그)나 CDN/게이트웨이 차단으로 DB 조회 자체를 없애는 것이 다음 단계다(범위 밖).
결론:
  품절 경로에서 잠금을 없애는 것이 선착순 트래픽 전체 처리량의 핵심이며, 조건부 UPDATE 는 성공 경로(잠금 최소)와 품절 경로(무잠금) 모두에서 최선이다.
```
