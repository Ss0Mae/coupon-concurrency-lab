# EXP-03 — HikariCP 풀 크기와 처리량 (동시 사용자 200명, 재고 무제한)

```text
실험 이름: poolsize — HikariCP maximum-pool-size 10 / 20 / 50, 비관적 락 vs 조건부 UPDATE
검증하려는 가설: 풀을 키우면 커넥션 대기가 줄어 TPS 가 오른다. (결과: 기각)
변경한 항목: HIKARI_POOL_SIZE 환경변수로 앱 재기동(minimum-idle = maximum-pool-size). 나머지 동일.
통제한 조건: 10초 지속 부하(constant-vus 200), 쿠폰 10,000,000개(품절 없음, 매 요청 새 사용자), 풀 크기별 워밍업 1회 후 5회 반복, 순서 회전
서버 및 DB 사양: EXP-01 과 동일 (MySQL max_connections=500)
테스트 데이터: coupon 1행(total_quantity=10,000,000), coupon_issue 0행
동시 사용자: 200
전체 요청 수: 10초 동안 도달한 요청 수 (풀·전략별 약 4,000~5,400건) × 2전략 × 3풀 × 5회
테스트 지속시간: 실행당 10초
```

| 구현 방식 | 풀 크기 | TPS | p95 | p99 | 커넥션 획득 평균 | 대기 커넥션 max | 행 잠금 대기 평균 | 행 잠금 대기 횟수 | MySQL CPU |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|

병목 원인:
  모든 요청이 같은 coupon 1행을 UPDATE 하므로 성공 발급은 "UPDATE ~ COMMIT(redo fsync)" 구간에서 직렬화된다.
  풀을 10 → 20 → 50 으로 키우면 그 직렬 구간에 줄 서는 트랜잭션이 늘어 행 잠금 1회당 대기가 17 → 42 → 119 ms 로 늘고,
  TPS 는 오르지 않는다(비관적 522 → 445 → 407, 조건부 468 → 413 → 419). 대기 커넥션 max 가 189 → 179 → 149 로 줄어도
  요청은 커넥션 대기 대신 행 잠금 대기로 옮겨 갈 뿐이다. MySQL CPU 15~19%(4 vCPU 기준 0.6 코어) 로 CPU 병목이 아니다.
해석:
  이 워크로드의 상한은 핫로우 1개의 커밋 직렬화(약 2 ms/건 ≈ 400~500 TPS)이고 커넥션 수는 병목이 아니다.
  풀 10 이 p95 434~460 ms 로 가장 좋고, 풀 50 은 p99 가 2~2.8초까지 늘어난다. HikariCP 의 "풀은 작게" 권고가 핫로우에서 그대로 재현됐다.
  비관적 락과 조건부 UPDATE 의 차이는 이 실험에서 작다(품절 경로가 없고 성공 경로는 둘 다 잠금 1회 + 커밋 1회).
부작용: 풀을 줄이면 핫로우가 아닌 다른 쿼리(조회 등)도 같은 풀을 쓰므로 실제 서비스에서는 워크로드 혼합을 보고 정해야 한다.
  10초 실행 5회의 편차가 크다(예: 조건부 풀 20 의 TPS 217~435). 같은 장비의 k6 부하와 fsync 지연 변동이 원인으로 보인다.
결론: 커넥션 풀 확대는 이 병목을 풀지 못한다. 근본 상한은 핫로우 커밋 직렬화이며, 이를 넘기려면 쿠폰 재고를 여러 행/버킷으로 나누거나
  Redis 같은 메모리 카운터로 재고 판정을 옮겨야 한다(이 저장소 범위 밖).
