# EXP-02 — 중복 요청: 사용자 1,000명이 각 2회 요청 (쿠폰 100개)

```text
실험 이름: duplicate — 쿠폰 100개, 사용자 1,000명 × 2회 = 요청 2,000건, 동시 사용자 1,000명
검증하려는 가설: 어느 전략이든 같은 사용자의 2번째 요청은 발급되지 않는다(중복 발급 0). 중복 차단은 UNIQUE(coupon_id, user_id) 제약이 담당한다.
변경한 항목: k6 USERS=1000, ITERATIONS=2000 (userId = 1 + i % 1000). 전략 외 코드·설정 동일.
통제한 조건: EXP-01 과 동일 (워밍업은 EXP-01 직후라 생략, 5회 반복, 순서 회전)
서버 및 DB 사양: EXP-01 과 동일
테스트 데이터: coupon 1행(total_quantity=100), coupon_issue 0행
동시 사용자: 1,000
전체 요청 수: 2,000 × 4전략 × 5회 = 40,000건
테스트 지속시간: 요청 2,000건 소진까지 (0.3~1.3초)
```

## 측정 결과 (5회 중앙값, 정합성 값은 5회 중 최악)

| 구현 방식 | 전체 요청 | 성공 응답 | 중복 차단(409) | 품절(410) | 5xx | DB 발급 건수 | 중복 발급 | 초과 발급 | TPS | p95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 락 없음 | 2,000 | 1,000 | 1,000 | 0 | 0 | 1,000 | 0 | 900 | 1,588.0 | 951.9 ms |
| 비관적 락 | 2,000 | 100 | 0 [0–15] | 1,900 | 0 | 100 | 0 | 0 | 3,657.4 | 254.7 ms |
| 낙관적 락 | 2,000 | 100 | 1 | 1,854 | 45 | 100 | 0 | 0 | 2,536.7 | 626.5 ms |
| 조건부 UPDATE | 2,000 | 100 | 0 | 1,900 | 0 | 100 | 0 | 0 | 6,130.4 | 186.3 ms |

```text
병목 원인: 이 실험은 정합성 검증이 목적이라 병목보다 응답 분류에 주목했다.
  비관적·조건부의 409 가 0 인 이유: 사용자의 2번째 요청이 도착할 때는 이미 품절이라 품절 경로(410)가 UNIQUE 검사(INSERT)보다 먼저 응답한다.
  비관적 락 3회차에 409 가 15건 나온 것은 품절 전에 2번째 요청이 도착한 경우다.
  락 없음은 품절이 나지 않으므로(EXP-01 참고) 2번째 요청 1,000건이 전부 INSERT 까지 가서 UNIQUE 위반 409 로 막혔다.
해석:
  네 전략 모두 DB 의 중복 발급은 0건 — 중복 방지는 락 전략이 아니라 UNIQUE 제약이 보장한다(EXP-04 에서 제약을 빼고 확인).
  락 없음은 중복은 막았지만 초과 발급 900건은 그대로다. 제약은 "같은 사용자 두 번"만 막지 "재고 초과"는 막지 못한다.
  쿠폰 100개 시나리오에서는 품절 경로가 먼저라 "중복 차단 수"가 전략의 성질을 보여 주지 못한다 → 재고가 남은 상태에서 재측정(EXP-07 dupopen).
부작용: 이미 발급받은 사용자가 품절 후 다시 요청하면 409(이미 발급) 대신 410(품절)을 받는다. 정합성에는 영향이 없지만 UX 관점에서는 별도 조회가 필요하다.
결론: 중복 발급 0건은 UNIQUE 제약으로 달성. 전략 비교의 성능 순위는 EXP-01 과 같다(조건부 6,130 > 비관적 3,657 > 낙관적 2,537 > 락 없음 1,588 TPS).
다음 실험: EXP-04 UNIQUE 제약 제거, EXP-07 재고가 남은 상태에서의 중복 요청.
```
